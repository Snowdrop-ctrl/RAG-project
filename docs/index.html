01

What is RAG

RAG stands for Retrieval-Augmented Generation. It means: retrieve the relevant text from our own documents first, then let the model generate an answer from that text instead of from its training data.

Nothing is retrained. The model is the same DeepSeek model either way — we simply change what sits next to the question in the prompt. Our app exposes both paths through one endpoint, POST /api/chat, switched by the mode field.

The four words that carry the whole idea
TermWhat it means here
ChunkA slice of a document. Ours are 200 words long
EmbeddingA chunk turned into 384 numbers that represent its meaning
Vector databaseWhere those numbers live, so we can search by meaning. We use ChromaDB
RetrievalFinding the chunks closest in meaning to the question
02

What problem RAG solves

A language model has one source of knowledge: whatever it read during training. That creates four problems the moment you ask it about your own company.

Four problems, and what changes with RAG
ProblemPlain LLMWith RAG
It invents answers Produces something fluent and plausible when it does not know The prompt says to use only the retrieved passages and to say so when they don't cover it
It never saw our files Our handbook, specs and contracts were never in its training data Those files are indexed locally and searched at question time
Training data goes stale Frozen at the training cut-off; a new policy is invisible to it Re-upload the document and the next answer already reflects it
No way to verify An answer arrives with no source to check Every answer carries the file name and page it came from

Both behaviours, measured on this build

# the answer is in the indexed handbook
Q: How many vacation days do I get?
A: You get 24 days of paid annual leave per calendar year, and unused
   leave can be carried over up to a maximum of 5 days [1].
   → matched a passage that never says "vacation" (score 0.59)

# the answer is in no indexed document
Q: What is the capital of Brazil?
A: The context passages do not contain the answer to that question.
   → refused instead of answering from training data

Worth using RAG for

  • Facts that change: policies, specs, tickets
  • Answers that must cite a source
  • Private documents the model never saw

RAG will not fix

  • Tone and formatting — that is prompting or fine-tuning
  • Reasoning the model cannot do anyway
  • Questions whose answer is in no document
03

RAG and the LLM: what happens when we ask a question

Five hops, about two seconds. Only the last one touches the internet.

The question pipeline at a glance

User presses ↑  in ChatInput.jsx
      │
      ▼
1. POST /api/chat      → { question, mode: "llm_rag" } via the Vite proxy
      │
      ▼
2. rag.retrieve()      → embed the question with the same model
      │                  search ChromaDB, keep the closest top_k = 4
      │                  drop anything under min_score = 0.35
      ▼
3. llm.py              → builds one prompt: rules + [1]…[4] + question
      │
      ▼
4. DeepSeek API        → writes the answer and cites [n]   (HTTPS)
      │
      ▼
5. { answer, sources } → chat bubble + source chips in MessageList.jsx

The prompt, and where the citations come from

llm.py builds one message: the rules, the retrieved chunks numbered [1]…[4], then the question. The [2] the model writes in its answer is the same [2] we handed it — that is the entire citation mechanism.

The real response, copied from a live run

{ "answer": "You get 24 days of paid annual leave per calendar year,
              and unused leave can be carried over up to 5 days [1].",
  "sources": [ { "label": "company-handbook.md",
                 "page":  null,
                 "score": 0.568 } ] }

Implementation flow: getting documents in

Before any question can be answered, documents have to be indexed. This runs once per file, when someone uploads it in the Docs panel or runs npm run ingest.

The upload pipeline at a glance

Upload document  (PDF · DOCX · TXT · MD)   POST /api/documents
      │
      ▼
1. Extract text        → pypdf / python-docx; page numbers kept
      │
      ▼
2. Chunk               → slices of 200 words, each repeating the
      │                  last 40 words of the slice before it
      ▼
3. Embed               → fastembed turns each chunk into a vector
      │                  of 384 numbers, on this machine
      ▼
4. Store in ChromaDB   → vector + chunk text + source file + page
                         saved under backend/data/chroma

05

Tech, tools and services

Everything runs locally except one thing: the call that writes the final answer. Embeddings do not need an account, so uploading and searching work offline.

What each piece does, and where it runs
ToolIts job hereRuns
React + ViteChat UI, Docs panel, mode dropdown; proxies /api in devlocal
FastAPIThe HTTP API, request validation, error mappinglocal
pypdf · python-docxPull text out of PDF and Word files, page by pagelocal
fastembedRuns bge-small-en-v1.5 on ONNX to make 384-number vectorslocal
ChromaDBStores vectors and does the cosine search; persists to a folderlocal
httpxMakes the HTTPS call to DeepSeeklocal
DeepSeek APIdeepseek-chat writes the final answerexternal
uv · pytest · ruffDependencies, 17 tests, linting. Tests stub the model calllocal

Run it

npm run setup once, then npm run dev starts the API on :8000 and the UI on :5173. API docs at /docs.

Swap any piece

Each service is one file behind a small function. Changing the vector database or the model provider means editing that file, not the pipeline.

06

Security: what leaves the machine

The question everyone asks is whether the model now has our documents. It does not: nothing is trained, and the model keeps no memory between requests. What is true is that the text of the retrieved chunks is sent to DeepSeek with every RAG question — roughly 800 words, over HTTPS.

  • Good Embedding runs locally. fastembed computes the 384 numbers on our machine, so uploading and indexing sends nothing anywhere.
  • Good The key is server-side only, in backend/.env, which git ignores. A key in frontend code is visible to every visitor in devtools.
  • Decide Check DeepSeek's retention and training terms before indexing anything confidential, and assume requests can be logged. If that is not acceptable for a document, don't index it.
  • To do There is no auth on the API. Anyone who reaches :8000 can upload, list, delete and query every document. Fix before this leaves localhost.
  • To do Chunks are untrusted input. An uploaded file can contain “ignore previous instructions”. Never let an answer trigger an action on its own.
  • Option Fully local is one file away. Point llm.py at a locally hosted model and nothing leaves at all — the rest of the pipeline is unchanged.

Try it yourself

Upload a document in the Docs panel, ask something it covers, then ask something it does not. The second answer should say the documents don't cover it — that is the system prompt working.

When answers are poor

  • Nothing relevant indexed — check the Docs panel
  • Scanned PDF with no text layer — extraction returns nothing
  • Wrong chunks retrieved — raise top_k or lower min_score
