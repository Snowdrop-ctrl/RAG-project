01

Why we need RAG, and the two modes

4 min

DeepSeek has never seen our documents. Ask it about our leave policy and it answers from its training data — confidently, and often wrongly. RAG means: find the relevant text in our own files first, put that text in the prompt, and let the model answer from it.

Our app has both, chosen by the dropdown. Both hit the same endpoint, POST /api/chat, with a different mode. The branch is four lines in app/api/chat.py.

The request our frontend sends

// frontend/src/services/chatService.js
POST /api/chat
{ "question": "How many vacation days do I get?",
  "mode":     "llm_rag" }
02

Uploading a document: chunking and embedding

7 min

This runs once per file, when someone uploads it in the Docs panel. Two words to get straight:

A chunk is a slice of the document — ours are 200 words long. An embedding is that chunk turned into a list of 384 numbers that represents its meaning. Chunks about the same subject end up with similar numbers, which is what makes search by meaning possible.

Doing it from the terminal instead of the UI

# put files in backend/data/docs/ then:
npm run ingest
  company-handbook.md: 1 chunks
  Indexed 1 file(s); 1 chunks total.
03

Asking a question: the full path

8 min

Five hops, about two seconds. The only step that touches the internet is the last one.

The numbers in app/config.py
SettingValueWhat it controls
chunk_words200How big each slice of the document is
chunk_overlap_words40How much each chunk repeats the previous one
top_k4How many chunks go into the prompt
min_score0.35How close a match must be to count at all
embedding_modelbge-small-en-v1.5Makes the 384 numbers. Change it and everything must be re-uploaded
deepseek_modeldeepseek-chatWrites the final answer
04

The prompt, and where citations come from

5 min

llm.py builds one message: a system prompt with the rules, the retrieved chunks numbered [1]…[4], then the question. The model is told to answer only from those passages and to cite them by number.

The real response, copied from a live run

{ "answer": "You get 24 days of paid annual leave per calendar year,
              and unused leave can be carried over up to 5 days [1].",
  "sources": [ { "label": "company-handbook.md",
                 "page":  null,
                 "score": 0.568 } ] }
05

What actually leaves the machine

6 min

Nothing about DeepSeek changes when we use it: our documents are not added to the model, and it keeps no memory between requests. What is true is that the text of the retrieved chunks is sent to DeepSeek with every RAG question — roughly 800 words, over HTTPS.

  • Good Embedding runs locally. fastembed computes the 384 numbers on our machine, so uploading and indexing sends nothing anywhere.
  • Good The key is server-side only, in backend/.env, which git ignores. A key in frontend code is visible to every visitor in devtools.
  • Decide Check DeepSeek's retention and training terms before indexing anything confidential, and assume requests can be logged. If that is not acceptable for a document, don't index it.
  • To do There is no auth on the API. Anyone who reaches :8000 can upload, list, delete and query every document. Fix before this leaves localhost.
  • To do Chunks are untrusted input. An uploaded file can contain “ignore previous instructions”. Never let an answer trigger an action on its own.
  • Option Fully local is one file away. Point llm.py at a locally hosted model and nothing leaves at all — the rest of the pipeline is unchanged.

Try it live

Upload a document in the Docs panel, ask something it covers, then ask something it does not. The second answer should say the documents don't cover it — that is the system prompt working.

When answers are poor

  • Nothing relevant indexed — check the Docs panel
  • Scanned PDF with no text layer — extraction returns nothing
  • Wrong chunks retrieved — raise top_k or lower min_score
